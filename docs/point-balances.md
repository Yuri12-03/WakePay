# ポイント残高

## 適用

demo-results.sql適用済みのSupabaseで、`supabase/point-balances.sql` の全文を **COMMIT; まで**実行してください。今回、共有DBへの適用は行っていません。

新規・既存ユーザーとも基準残高は2,000 WPです。導入時点で全員回答済みのデモは対象外として記録し、後から同じ回答が再送されても加算しません。導入時点で未確定のデモは、その後に全員回答した時点で反映します。

ホームのプロフィール横に残高を表示し、約3秒ごとに更新します。デモ結果にも本人の最新残高を表示します。DB未更新で残高を取得できない場合、仮の2,000を表示せず取得できない旨を表示します。

## 保存方式

`wp_point_settlements` は部屋・回ごとの確定・対象外・取消を記録し、`wp_point_entries` は参加者ごとの増減を記録します。残高は2,000＋取消されていない増減の合計です。二重反映は部屋・回の主キーで防ぎます。

最後の回答と残高反映は同一トランザクションです。リセットはその回の増減を取消にし、他の部屋や他の回の増減を保持します。残高がマイナスでも、作成・参加を制限せず、ポイントの事前確保は行いません。

初期値はDB側で決定し、クライアントから残高や増減額を受け付けません。テーブル直接アクセスと内部残高関数の直接呼び出しは禁止しています。

このSQLの後に旧demo-results.sqlやphase2.sqlを再適用すると関数が古い定義に戻るため、適用順序を守ってください。

## 検証

本番ビルド成功。SQL・入力検証など47件のテスト成功（PGliteの隔離DB）。旧結果の除外、新規登録2,000、二重反映防止、他部屋を維持した取消、全員成功・失敗、マイナス残高での作成・参加、再適用、アクセス制御を検証。

画面テストはAPIテストデータを使用します。共有Supabaseでの実接続・複数接続の同時処理は適用後に確認してください。
画面テスト成功：3端末相当・390px幅で、ホームの残高2,051 WP表示とリセット後2,000 WPへの自動更新を確認しました。
