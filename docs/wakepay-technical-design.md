# WakePay 技術設計ドキュメント

改訂日：2026-09-17

大学の授業で作成するプロトタイプ向け。9月16日版を、フェーズ3・自己申告デモ・WP残高管理の実装と9月17日の決定事項に合わせて改訂する。
本書は実装済み仕様と今後の目標を区別する。「実装済み」はローカルコードと移行SQLが存在する意味であり、共有Supabaseへの適用や公開環境への反映まで確認できたことを意味しない。照合対象はコミット4a83b6dまでのコード。

## 1. 今回の変更と決定事項

### 確定した変更

- 部屋作成時に、作成者がグループ名・参加予定人数・起床日・起床時刻・チャレンジ金額を設定する。
- 起床日は作成者が選択する。全員の表示・日付解釈は日本時間（Asia/Tokyo）で統一する。
- チャレンジ金額は **100〜2000 WP**。100と2000を含む。
- 起床時刻は **00:00〜23:59**。時間帯制限を撤廃し、両端を含む。選択した日付と組み合わせて未来の日時でなければならない。
- コード入力の次に部屋の条件を表示する。この段階では参加登録しない。
- 参加希望者が「この条件で参加する」か「参加しない」を選択する。
- 「この条件で参加する」で参加登録と条件同意を記録する。辞退は記録を追加せず、入力画面に戻る。
- 作成後は起床日・起床時刻・チャレンジ金額を変更できない。
- 全員が条件に同意して参加したら、自動開始する。作成者の開始ボタンや、同じ条件への再承認は設けない。

### 補足の設計判断

- 金額は整数、入力刻みは1 WPとする。100 WP刻みという追加制限は設けない。
- 時刻は1分単位、秒は00。日付は今日以降を選択可能とし、過去の日時はAPI・DBで拒否する。業務上の将来日数制限は設けない。ただし現実装の入力形式・SQLは西暦1〜9999年を扱い、画面の日付上限は9999-12-31。
- プレビューにより人数枠は予約しない。参加確定時に定員・条件・受付状態・起床日時を再確認する。
- 実際のお金の決済は行わず、WPは架空ポイントとして扱う。

| 作成後の条件変更 | 変更不可 | 変更API・再承認画面・条件の版管理は追加しない |

初回条件の設定・参加同意はフェーズ2.5、全員参加を受けた開始・待機はフェーズ3として実装済み。

## 2. 利用の流れ

```text
トップ → 登録 → ホーム
                 ├─ 部屋作成：名前・人数・起床日・時刻・金額を入力
                 │    └─ 作成者自身も条件に同意して参加 → 部屋コード発行
                 └─ 部屋コード入力 → 条件確認
                                      ├─ この条件で参加する → 部屋ページ
                                      └─ 参加しない → コード入力へ戻る

部屋ページ → 全員の参加・同意が成立 → 自動開始 → 待機画面
  ├─ 現在：各自がデモで成功／失敗を回答 → 全員回答 → 分配・残高反映
  │          ↑ 作成者がリセット（当該回の増減を取り消す）
  └─ 将来：実際の3回の起床確認 → 最終締切後の判定・結果（未実装）
```

部屋作成者も2〜8人の定員に含める。登録・部屋作成・参加者一覧はフェーズ2の機能を拡張する。

## 3. 画面と必要な機能

条件確認を `/join-room` 内の次のステップとして表示する。下表の1〜7は実装済み、8・9は将来予定で未実装。デモ結果は7の待機画面内で表示するため専用画面は増やさない。このほか独立した既存アラーム試作 `/alarm-demo` があるが、部屋や3回の確認とは連動していない。

| # | 画面 | URL | 主な表示・操作 |
| --- | --- | --- | --- |
| 1 | トップ | `/` | ロゴ・紹介・利用開始。登録済みならホームへ |
| 2 | 登録 | `/register` | ニックネーム・プリセットアイコン |
| 3 | ホーム | `/home` | 自分の情報・WP残高・作成・コード参加・参加済みの部屋 |
| 4 | 部屋作成 | `/create-room` | 部屋名・人数・起床日・時刻・金額を指定して作成 |
| 5 | コード入力・条件確認 | `/join-room` | コードで検索 → 条件を表示 → 参加／辞退 |
| 6 | 部屋ページ | `/room/[roomCode]` | 条件・参加者・人数・準備状況 |
| 7 | 待機 | `/room/[roomCode]/waiting` | 起床日時・金額・確認予定・残り時間・デモ回答／分配／リセット |
| 8 | アラーム・起床確認 | `/room/[roomCode]/alarm` | 現在時刻・3回の確認状態・残り時間・音 |
| 9 | 結果 | `/room/[roomCode]/result` | 成功／失敗・確認時刻・WP分配 |

### 登録・ホーム

- ニックネームは1〜20文字、アイコンはプリセットから選ぶ。
- Supabase匿名Authで発行されたIDに、`users` のプロフィールを対応させる。
- AuthトークンはHttpOnly Cookieに保存し、APIが本人を確認する。ブラウザから送られたユーザーIDを本人証明にしない。
- ホームでは作成・参加ボタンと参加済みの部屋を表示する。プロフィール横の案内文は「残高：○○ WP」に変更。本人の残高は約3秒ごとに再取得する。取得失敗時に仮の2,000 WPを表示しない。
- Cookie削除や別端末からのアカウント復旧はプロトタイプの対象外。

### 部屋作成

| 入力 | ルール | 例 |
| --- | --- | --- |
| グループ名 | 空白のみ不可、1〜40文字 | 1限ぜったい間に合う会 |
| 参加予定人数 | 作成者込み2〜8人 | 4人 |
| 起床日 | 作成者が選択、日本時間 | 2026-09-17 |
| 起床時刻 | 00:00〜23:59、1分単位 | 07:00 |
| チャレンジ金額 | 100〜2000 WP、整数 | 500 WP |

- 作成ボタンは「この条件で部屋を作成して参加する」とし、作成者自身の参加も明示する。
- 保存前に起床日・時刻・金額を確認できるよう、同じ画面に入力内容を表示する。
- 条件・部屋・作成者の参加をまとめて保存し、失敗時は部屋だけが残らないようにする。
- 作成成功後に6文字の部屋コードを表示し、部屋ページへ遷移する。
- 作成前のフォームに金額・日付・時刻を勝手に確定させない。利用者が選択した値を送信する。
- 「作成後は条件を変更できません」と表示する。条件を変えて参加したい場合は別の部屋を新規作成する。旧部屋からの退出・取消・条件変更を自動で行わない。

### コード入力・条件確認

1. 半角英数字6文字のコードを入力し、「部屋の条件を確認する」を押す。
2. 部屋名、現在人数／定員、起床日・時刻（日本時間）、1人あたりのチャレンジ金額を表示する。
3. 「この条件で参加する」「参加しない」を表示する。
4. 同意した場合のみ参加APIを呼ぶ。成功後に部屋ページへ進む。

例：**2026年9月17日 07:00（日本時間）／500 WP／参加者2人・定員4人**。

- 確認画面を見ただけでは参加者を増やさない。
- 辞退・戻る・タブを閉じる操作では参加登録しない。辞退者一覧も作らない。
- 満員・受付終了・起床日時経過・条件未設定の旧部屋は理由を表示し、新規参加を許可しない。
- すでに参加済みなら「参加済みです／部屋へ進む」を表示し、重複参加を作らない。
- プレビュー後に状況が変わった場合は、参加確定APIの結果を表示する。満員になっても無理に参加させない。
- 入力コードを変更したら古い条件表示を破棄する。遅れて返ってきた以前のコードの取得結果を表示しない。
- 参加前には参加者の氏名・アイコン・ユーザーID一覧を見せない。

### 部屋ページ

- グループ名・コード・起床日時・金額・参加者一覧・人数を表示する。
- 参加者一覧は5秒おきに更新する。
- 現在はフェーズ3まで実装済み。アラームの本機能は未実装。
- 旧フェーズ2.5単独のDBでは全員参加で `ready` となる。現在の画面で `ready` が残る場合は開始未完了として管理担当者への確認を案内する。
- フェーズ3のSQL適用後は最後の参加確定で自動的に `active` へ進み、部屋ページを見ている全員を状態更新に応じて待機画面へ案内する。開始ボタン・条件編集ボタンは置かない。

### 待機・起床確認・結果

- 待機画面では、固定文言の「明日」だけでなく、保存済みの実際の起床日時を表示する。
- 起床日時は現在時刻から毎回計算し直さず、部屋が保存した `wake_at` を使う。
- 実装済みの待機画面は本人の3回分の受付開始・締切と、サーバー時刻を基準にした起床までの残り時間を表示する。待機情報は5秒ごとに再取得。起床時刻到達後も未実装のalarm/resultへは移動しない。
- 将来のアラーム画面は3回の確認操作と確認状態を表示する（未実装）。
- 将来の結果画面は実際の起床判定を表示する（未実装）。現在のデモは待機画面内に全員の自己申告結果・増減WP・本人の残高を表示し、全員回答で確定する。実際の最終締切を待たない。

### 旧設計との関係

旧設計の「全員集合 → 設定 → 全員承認」は、「作成時に設定 → 参加前に条件確認・同意」へ移す。
初回条件を設定するための `/setting` と、同じ条件を二重に承認するための `/confirm` は廃止予定の設計ルートとして扱い、新たに実装しない。作成後の条件変更・再承認も設けない。

## 5. データベース

基本4テーブルにデモ用2テーブル、残高履歴用2テーブルを追加し、計8テーブルを使用する。`rooms.wake_at` はフェーズ2.5で追加済み。`users` に残高列は追加せず、履歴から計算する。
全体の移行手順は [フェーズ2.5 DB引き継ぎ書](phase2.5-db-handoff.md) を参照する。

### users

| 列 | 型 | 意味 |
| --- | --- | --- |
| id | text、主キー | Supabase匿名AuthのユーザーID |
| nickname | text | ニックネーム |
| icon | text | アイコン識別子 |
| created_at | timestamp | 登録日時 |

今回の列変更はない。

### rooms

| 列 | 型 | 意味・制約 |
| --- | --- | --- |
| id | text、主キー | 部屋ID |
| room_code | text、unique | 部屋コード |
| group_name | text | グループ名 |
| max_members | integer | 作成者込み2〜8人 |
| creator_id | text、usersへの参照 | 作成者 |
| wake_time | time | 日本時間の00:00〜23:59、秒00。既存列を利用 |
| wake_at | **timestamptz、新規** | 選択した日付・時刻からDBが確定する共通の起床日時 |
| challenge_amount | integer | 1人あたり100〜2000 WP。既存列を利用 |
| status | text | waiting / ready / active / finished |
| created_at | timestamp | 作成日時 |

日付だけの列は追加せず、選択した日付と時刻を `wake_at` にまとめて保存する。
`wake_at` が基準で、`wake_time` はその日本時間の時刻と一致させる。新規部屋では3項目を必須とするが、旧データを保持する移行中は列としてNULLが残ることがある。

### room_members

| 列 | 型 | 意味・制約 |
| --- | --- | --- |
| id | text、主キー | 参加レコードID |
| room_id | text、roomsへの参照 | 参加先 |
| user_id | text、usersへの参照 | 参加者 |
| approved | boolean | 部屋条件に同意して参加しているか |
| joined_at | timestamp | 参加日時 |

同じ部屋・ユーザーの組み合わせは1件まで。作成者も作成時に条件へ同意し、新仕様では作成・参加時に `approved=true` を保存する。
旧部屋のfalseを一括でtrueにはしない。作成後の条件変更を認めないため、条件の版管理や再承認用の列は追加しない。

### wake_checks

| 列 | 型 | 意味 |
| --- | --- | --- |
| id | text、主キー | 確認レコードID |
| room_id | text | 部屋ID |
| user_id | text | 参加者ID |
| check_number | integer | 1・2・3 |
| checked_at | timestamptz | 未確認ならNULL。確認時刻はサーバーが記録 |
| deadline | timestamptz | 各確認の締切 |

フェーズ2.5では確認レコードを作らない。部屋作成時は全参加者が未確定のため、フェーズ3の開始処理で全員分を作成する。
フェーズ3のSQLで `(room_id, user_id, check_number)` の一意性、番号1〜3、部屋・ユーザー参照のNOT NULLを追加する。checked_at・deadlineはtimestamptzへ移行する。旧timestamp値がある場合、保存元タイムゾーンを確認しない限り移行を停止する。デモはwake_checksを更新しない。

### デモ・残高の追加テーブル

| テーブル | 主な列・キー | 役割 |
| --- | --- | --- |
| wp_demo_rounds | room_id（主キー・rooms参照）、round（正の整数） | 部屋ごとの現在のデモ回数。初期1 |
| wp_demo_answers | room_id・user_id（複合主キー）、success、submitted_at（timestamptz） | 現在の回の本人回答。リセットで削除 |
| wp_point_settlements | room_id・round（複合主キー）、excluded、reversed | 回ごとの確定、導入前対象外、取り消しを記録 |
| wp_point_entries | room_id・round・user_id（複合主キー）、delta（integer） | 各参加者のポイント増減。settlementsへ複合外部キー |

各テーブルはRLS有効、PUBLIC・anon・authenticatedからの直接アクセスを禁止し、認証付きRPC経由で利用する。リセット後もポイント履歴は保持し、reversedで合計から除外する。

## 6. APIとデータの受け渡し

すべての操作でAPIがCookieから認証を確認し、DB側でも `auth.uid()` によって本人を確定する。部屋コードを知っているだけで全テーブルを読める状態にはしない。

| API | メソッド | 役割・担当フェーズ |
| --- | --- | --- |
| `/api/users` | POST | 登録。フェーズ2 |
| `/api/users` | GET | 自分のプロフィールと計算済みbalance（実装済み） |
| `/api/users/[id]` | GET | 自分のIDのプロフィール。フェーズ2 |
| `/api/rooms` | GET | 参加済みの部屋。フェーズ2 |
| `/api/rooms` | POST | 条件付き部屋作成へ変更。フェーズ2.5 |
| `/api/rooms/[roomCode]/preview` | GET | 参加前の条件確認。フェーズ2.5で追加 |
| `/api/rooms/[roomCode]/join` | POST | 条件同意を伴う参加へ変更。フェーズ2.5 |
| `/api/rooms/[roomCode]` | GET | 参加者限定の部屋情報・条件・参加者一覧 |
| `/api/rooms/[roomCode]/waiting` | GET | 部屋・本人の確認予定・server_now（実装済み） |
| `/api/rooms/[roomCode]/demo` | GET | 回数・全員の回答・増減・本人の残高（実装済み） |

| `/api/rooms/[roomCode]/result` | GET | 実際の起床判定の結果。フェーズ5・未実装 |

上記は14個のHTTP操作で、11個が実装済み、checkのGET/POSTとresultのGETの3個は未実装。デモPOSTは回答とリセットで共通。手動開始・条件変更・再承認のAPIは追加しない。旧 `/setting`・`/approve` は新たに実装しない。
自動開始は最後の参加を確定するDB処理から内部的に呼び出し、クライアントが別APIを呼ぶことには依存しない。

### 部屋作成

`POST /api/rooms`

```json
{
  "group_name": "朝活チーム",
  "max_members": 4,
  "wake_date": "2026-09-17",
  "wake_time": "07:00",
  "challenge_amount": 500
}
```

API・DBは不正な日付、範囲外の時刻、現在以前の日時、不正金額を拒否する。
日付・時刻は日本時間として解釈し、DBが `wake_at` を確定する。応答は201 `{ "room": Room }`。
例の起床日時は `2026-09-17T07:00:00+09:00`（UTCでは前日22:00）となる。

### 条件プレビュー

`GET /api/rooms/ABC123/preview` の200応答例：

```json
{
  "room": {
    "room_code": "ABC123",
    "group_name": "朝活チーム",
    "max_members": 4,
    "member_count": 2,
    "wake_at": "2026-09-17T07:00:00+09:00",
    "challenge_amount": 500,
    "status": "waiting"
  },
  "is_member": false,
  "can_join": true,
  "unavailable_reason": null
}
```

参加不可理由は `full` / `closed` / `expired` / `conditions_missing`。すでに参加済みなら `is_member=true`、`can_join=false` とし、部屋へのリンクを表示する。理由は同時に複数成立し得るため、旧条件未設定 → 期限経過 → 受付終了 → 満員の順に表示理由を決める。
存在しないコードは404。未登録・未認証は401。参加者の詳細一覧は返さない。

### 条件同意と参加

`POST /api/rooms/ABC123/join`

```json
{
  "accepted": true,
  "expected_conditions": {
    "wake_at": "2026-09-17T07:00:00+09:00",
    "challenge_amount": 500
  }
}
```

- `accepted=true` と表示済み条件を必須にする。辞退時はAPIを呼ばない。
- DBに保存された条件と一致するか確認する。日時は文字列の表記ではなく同一の瞬間として比較する。
- 不一致なら409で再確認を求め、未確認の新条件で勝手に登録しない。
- 定員・受付状態・起床日時も参加確定時に再検証する。
- 200 `{ "room": Room }` を返す。同一ユーザーからの再送は重複登録せず成功を返す。
- フェーズ2のコードだけによる参加RPCを残して、新しい同意確認を迂回できる状態にしない。

エラー形式はフェーズ2と同じ `{ "error": { "message": "日本語メッセージ" } }` とし、入力400、認証401、権限403、部屋なし404、条件不一致・参加不可409、接続・設定502/503を使う。

### 待機・デモ・残高のデータ契約

- waiting GET：`{ room, checks: [{ check_number, opens_at, deadline }], server_now }`。
- demo GET／POST応答：`{ round, user_id, can_reset, complete, answered, total, amount, pool, success_count, members, balance, balance_applied }`。
- members：`[{ user_id, nickname, icon, success, delta }]`。未回答のsuccessはnull、全員回答前のdelta・poolはnull。deltaは増減であって残高ではない。
- 回答POST：`{ "action": "answer", "round": 1, "success": true }`。失敗はfalse。
- リセットPOST：`{ "action": "reset", "round": 1 }`。作成者のみ。
- 現在のroundと異なる送信は409。既回答と同じ回答の再送は成功、異なる回答は409。
- balanceは本人分だけ。users GET／自分のIDのGETでも取得する。SQL未適用時は欠落し得るため画面で取得不可を案内する。
- balance_appliedはその回が残高に反映済みかを示す。導入前の確定結果ではfalse。
- 作成・参加APIは、RPCの部屋オブジェクト直接返却と `{ room: ... }` の双方を受け入れ、API応答は `{ room: Room }` にそろえる。

## 7. 保存と開始の流れ

```text
画面 → Next.js API → Supabase Authで本人確認 → DBの権限付きRPC
```

### 部屋作成・参加

1. 作成RPCが条件を検証し、部屋と作成者の同意済み参加を同一トランザクションで保存する。
2. プレビューRPCは条件と参加可否だけを返し、書き込まない。
3. 参加RPCは対象の部屋行をロックし、条件同意・定員・受付状態を検証して参加者を追加する。
4. フェーズ2.5では最後の参加を保存して `ready` にする。フェーズ3では、その同じトランザクション内で開始処理を実行して `active` にする。

| 状態 | 意味 |
| --- | --- |
| waiting | 条件は確定済みで参加者を募集中 |
| ready | 定員に達し全員同意済み。フェーズ2.5単独ではここまで。フェーズ3では自動開始の内部的な移行状態 |
| active | 全員分の確認データが作成され、開始済み。起床時刻まで待機 |
| finished | 将来の本機能での結果確定状態。現デモはこの状態へ変更しない |

### 開始処理の共通要件（フェーズ3）

- 人数が定員に達していること、全員が現在の条件に同意していること、起床日時が未来であることをDBで確認する。
- 部屋が `active` になることと、参加者ごとの3件の `wake_checks` がそろうことを同一トランザクションで保証する。
- 繰り返し呼ばれても確認レコードを重複作成しない。
- フェーズ3では最後の参加追加・確認レコード生成・activeへの変更をまとめて確定する。失敗した場合は最後の参加追加も取り消し、再試行できるようにする。
- ブラウザを閉じても、別の開始ボタンを押さなくても、最後の参加処理で開始が成立する。
- 開始後は新規参加を許可しない。すでに参加済みの人の閲覧・再アクセスは許可する。
- 定員に達しないまま起床日時を過ぎた部屋は開始せず、受付期限切れとして表示する。この場合はチャレンジ不成立でWPの増減を発生させない。
- `finished` は開始したチャレンジの全確認期限が過ぎて結果が確定した状態に使う。開始していない受付期限切れは成功／失敗と混同しない。

## 8. 実際の起床確認（3回）：予定生成は実装済み、確認操作・判定は未実装

部屋の `wake_at` を基準に、起床時刻・10分後・20分後に受付を開始する。押した時刻を基準に次回をずらさない。

| 回数 | 受付開始 | 締切 | 07:00起床の例 |
| --- | --- | --- | --- |
| 1 | wake_at | wake_at + 10分 | 07:00以上、07:10未満 |
| 2 | wake_at + 10分 | wake_at + 20分 | 07:10以上、07:20未満 |
| 3 | wake_at + 20分 | wake_at + 30分 | 07:20以上、07:30未満 |

23:59起床なら、締切は翌日の00:09・00:19・00:29。日付をまたいでも保存済みのwake_atから計算する。

以下の実際の確認操作はフェーズ4の目標仕様であり、デモボタンには適用しない。
- 確認画面は毎秒、保存された開始・締切日時との差分で残り時間を表示する。
- サーバーが時刻を記録する。クライアントが送った確認時刻をそのまま保存しない。
- 受付前・締切以降の確認は拒否する。締切と同時刻は期限切れ。
- 早い回の未確認を後の回で埋めることはできない。重複送信は同じ確認結果を返す。
- ブラウザ表示の時計とサーバー判定がずれた場合はサーバーを正とする。

## 9. 実際の成功・失敗とWP分配：本機能は未実装

開始済みのチャレンジで、全員の最終締切を過ぎた後に結果を確定する。

- 3回すべてがそれぞれの受付時間内に確認済み：成功。
- 1回でも未確認または受付時間外：失敗。
- 開始前・実行中：未確定。未確認があるだけで最終失敗と表示しない。

```text
失敗者の合計WP = チャレンジ金額 × 失敗者数
成功者1人あたりの分配 = floor(失敗者の合計WP ÷ 成功者数)
```

4人で500 WP、失敗者1人なら成功者3人へ166 WPずつ、端数2 WPを最も早く起きた成功者へ加算する。
「早い」は第1回の確認時刻で比較する。同時刻の場合の端数の受取人はフェーズ5の実装前に決定する。
全員成功なら増減なし。全員失敗なら全員が設定金額を失い、分配はなし。実際の送金は行わない。累計WP残高は9月17日追加仕様として実装済み（第14・15節）。実際の起床判定と残高の連動は今後の実装対象で、デモとの二重計上を防ぐ設計が必要。

### 利用と結果確定

- 全員参加してactiveになった部屋の待機画面で利用する。finishedの部屋も取得対象だが、デモ自身は部屋の状態を変更しない。

### リセット・競合対策

- 部屋作成者のみ「結果をリセットする」→確認操作で全員分をリセットできる。途中の回答もリセット可能。
- 回答はリセットまで変更できない。同じ回答の再送は重複登録しない。
- リセットでroundを増加させる。旧roundの回答・二重リセットは409で拒否し、次の回へ混入させない。
- 回答・リセットは同じ部屋行のロックで直列化する。
- 実際のwake_checks、起床日時、部屋状態を変更しない。新しい部屋を作り直す必要はない。

## 15. WP残高（実装済み）

### ユーザー決定事項

- 新規・既存ユーザーとも基準残高は **2,000 WP**。
- 導入前に全員回答済みのデモ結果は残高へ遡及反映しない。再送で反映されることも防ぐ。
- 導入時点で未確定のデモは、その後に全員回答して確定した時点で反映する。
- ホームの「友達と早起きの準備をしましょう。」を「残高：○○ WP」に変更する。
- 残高不足・マイナスでも作成・参加できる。参加時の引き落とし・ポイント確保は行わない。
- リセットはその回で増減した残高のみ取り消す。他の部屋・他の回の増減は維持する。

### 計算と保存

```text
残高 = 2,000 + 対象外でも取消済みでもない確定履歴のdelta合計
```

usersに残高列を置かず、内部関数wp_balanceが履歴からbigintで計算する。wp_current_userがプロフィールにbalanceを追加し、wp_demo_roomも本人のbalanceとbalance_appliedを返す。

最後の回答・確定履歴・参加者の増減記録を同一トランザクションで保存する。部屋×回の主キーにより同じ結果を二重反映しない。リセットは当該確定履歴をreversed=trueにし、履歴自体は保持する。

移行時点で完了済みの回はexcluded=trueとして記録する。SQLを再実行しても既存の残高を2,000へ上書きせず、過去の確定履歴も重複作成しない。

wp_balanceをクライアントから直接実行する権限は与えない。残高・deltaをクライアント入力として受け取らず、DBの参加者・回答・条件から計算する。

### 表示例

| 操作 | 残高2,000 WPからの例 |
| --- | --- |
| デモ結果が+50 WP | 2,050 WP |
| デモ結果が−100 WP | 1,900 WP |
| 上記−100 WPの回をリセット | その回の−100のみ取り消し、2,000 WPへ戻る |
| 他の部屋で+200 WPがある状態で−100の回をリセット | +200は維持し、2,200 WP |
| 合計損失が2,100 WP | −100 WP。作成・参加は継続可能 |

### 実DBで判明した差異と対応

実DBの作成関数にはリポジトリと異なる定義があり、時間外の入力で日本語の例外を返していた。また、制約名がリポジトリのwp_wake_time_rangeとは別の **rooms_wake_time_range** で、これが残ると23514となり作成が失敗した。

後者への修正は会話で別途案内したもので、現行phase3-any-time.sqlには含まれていない。同じ制約がある環境を再構築する場合の補足SQLは以下。既存データは変更・削除せず、新規書き込みを24時間・1分単位に制限する。

```sql
BEGIN;
ALTER TABLE public.rooms DROP CONSTRAINT IF EXISTS rooms_wake_time_range;
ALTER TABLE public.rooms ADD CONSTRAINT rooms_wake_time_range CHECK (
  wake_time >= TIME '00:00'
  AND wake_time < TIME '24:00'
  AND EXTRACT(SECOND FROM wake_time) = 0
) NOT VALID;
COMMIT;
```

502というHTTPステータスだけで接続障害とは断定しない。共通メッセージに変換されるDB例外もあるため、発生時刻のSupabase Postgresログで制約名・関数を確認する。
