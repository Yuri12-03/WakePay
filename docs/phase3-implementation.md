# フェーズ3の実装と時刻制限解除（2026-09-17）

## 現在の動作

- 最後の参加で、適用済みの `wp_join_room_v25` が全員の確認予定を生成し、同じトランザクションでactiveへ移行します。
- 部屋ページは5秒ごとの取得でactive/finishedを検出し、`/room/[roomCode]/waiting` へ移動します。最後の参加者も同じ経路で待機へ進みます。
- `GET /api/rooms/[roomCode]/waiting` は認証後に読み取り専用の `wp_waiting_room` を呼びます。
- 待機画面は部屋条件、本人の3回分の確認予定、日本時間の日付、サーバー時刻基準の残り時間を表示します。
- 起床時刻になっても未実装のalarm/resultルートへは移動しません。起床確認・音の再生・結果・WP分配が未提供であることを表示します。
- 時刻は00:00〜23:59、1分単位に変更しました。日本時間・未来日時・100〜2000 WP・作成後変更不可は維持します。

## 必要なDB追加作業

利用者から、Downloadsの `phase3.sql` は適用済みとの申告があります。添付と同じSQLを `supabase/phase3.sql` に保存しました。こちらから共有DBへの再適用は行っていません。

**起床時刻の制限解除には `supabase/phase3-any-time.sql` 全体を追加で適用してください。** アプリだけを変更しても、既存DBが04:00〜11:00以外を拒否します。

追加SQLはトランザクション内で、時刻の制約と次の4関数を更新します。

- `wp_guard_room_conditions`
- `wp_room_unavailable_reason`
- `wp_create_room_v25`
- `wp_start_room`

作成RPCの戻り値はリポジトリと同じ部屋オブジェクトです。アプリは部屋オブジェクトと `{ room: ... }` の両方に対応しています。参加RPC・待機RPCは変更しません。既存の日時・参加者・確認データを変更・削除しません。

適用順序は `phase2.sql` → `phase2.5.sql` → `phase3.sql` → `phase3-any-time.sql`。旧SQLを後から再適用すると制限や動作が戻るため、最終状態に注意してください。追加SQLは再実行可能です。

この追加SQLの共有DBへの適用は未実施です。SQL適用後に、別アカウントで00:00や23:59の部屋を作成・条件確認・参加し、全員が待機へ進むことを確認してください。同時参加は本物のPostgreSQLの別接続で確認する必要があります。

`npm.cmd run build` と `npm.cmd test --prefix tests` を使用します。SQLテストは実DBと隔離したPGlite上で動作します。画面テストは明示的なAPIテストデータを使い、共有DBへ書き込みません。
