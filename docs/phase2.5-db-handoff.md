# フェーズ2.5：DB担当者への引き継ぎ

更新日：2026-09-16

対応する仕様：[改訂技術設計書](wakepay-technical-design.md)。

この文書は設計変更とDB移行の引き継ぎです。移行SQL `supabase/phase2.5.sql` と画面・APIは実装済みです。共有DBへの適用は行っていません。
前提は、提示済みの4テーブルと `supabase/phase2.sql` が適用されていることです。フェーズ2の匿名サインインと追加SQLは、担当者から適用完了の報告を受けています。

## 1. 変更する体験

1. 作成者が部屋名・人数に加え、起床日・起床時刻・チャレンジ金額を指定して部屋を作る。
2. 参加希望者が部屋コードを入力すると、まず条件を表示する。この時点では参加登録しない。
3. 「この条件で参加する」で初めて参加登録する。「参加しない」ではDBに何も追加しない。
4. 部屋ページでも、全員が同じ金額と起床日時を確認できる。
5. 作成後の起床日・時刻・金額は変更しない。全員参加で再承認なしの自動開始へ進む（開始の実装はフェーズ3）。

確定要件：金額は100〜2000 WP（両端を含む）、起床時刻は04:00〜11:00（両端を含む）。WPは架空ポイントであり、今回の変更では残高管理・実送金を追加しない。

## 2. DB変更は必要か

**必要です。ただし金額・時刻用のテーブルを新しく作る必要はありません。**

| 対象 | 現在 | 必要な変更 |
| --- | --- | --- |
| `rooms.challenge_amount` | nullableなinteger。フェーズ2では保存していない | 新規部屋作成時に必須。100〜2000の整数に制限 |
| `rooms.wake_time` | nullableなtime。フェーズ2では保存していない | 新規部屋作成時に必須。04:00〜11:00、秒は00に制限 |
| `rooms.wake_at` | なし | 作成者が選んだ起床日・時刻を保存するtimestamptzを追加。日本時間で解釈 |
| `room_members.approved` | デフォルトfalse | 条件への同意を伴う作成・参加ではtrueを明示して保存 |
| 部屋条件の事前取得 | なし。`wp_get_room` は参加者限定 | 参加前に条件だけを取得できるRPCを追加 |
| `wp_create_room` | 部屋名・人数の2引数 | 金額・起床時間も受け取り、検証・保存する新しいRPCを追加 |
| `wp_join_room` | コードのみで参加できる | 条件同意の検証付きRPCへ置き換える |
| `wp_get_room` / `wp_my_rooms` | 参加済みの部屋の取得 | 金額・起床日時・参加可否を新しい型とそろえる |
| 条件の変更禁止 | 条件変更を防ぐ仕組みなし | `wake_at`・`wake_time`・`challenge_amount` の変更を拒否するDBトリガーを追加。通常のstatus更新は許可 |
| `wake_checks` | 起床確認用 | フェーズ2.5でレコードを作らない。フェーズ3の開始処理で作成する設計に変更 |

`users` の列変更は不要です。メール認証の追加や匿名サインインの再設定も不要です。

## 3. 検証と保存のルール

- 金額はWP単位の整数。入力刻みは1 WP。100 WP刻みには制限しない。
- 起床時刻は日本時間で1分単位。04:00と11:00は有効、03:59・11:01・秒付きの値は無効。
- ブラウザの入力制限だけに頼らず、Next.js APIとDB関数の両方で検証する。
- DBにも範囲のCHECK制約を追加する。NULLを許す移行期間中は、CHECKだけで必須化されたと考えない。新規作成RPCではNULLを明示的に拒否する。
- `wake_at` は日付・タイムゾーンを含む共通の起床予定日時。表示は `Asia/Tokyo` に統一し、「明日」だけでなく実際の日付も表示する。
- 作成者が日付を選ぶ。APIの `wake_date`（YYYY-MM-DD）と `wake_time`（HH:mm）をDBで日本時間として結合する。今日以降を選択可能とし、現在以前の日時は拒否する。将来日付の上限は今回設けない。
- `wake_time` は `wake_at` を日本時間に変換した時刻と一致させる。両方をクライアントから別々に受け取って信用しない。
- 現在時刻より未来であることは作成・新規参加・開始の各処理でサーバー時刻を使って検証する。時間の経過で不正になるような `wake_at > now()` のCHECK制約は作らない。
- 最終参加枠の競合は、現在の部屋行ロックとユニークインデックスを維持して防ぐ。
- 作成者の参加レコードも `approved=true`。作成操作の文言で、その条件で自身も参加することを伝える。
- 条件変更禁止のトリガーは3列をNULLも含めて比較し、値が変わるUPDATEだけを拒否する。同値の更新やstatusの遷移まで禁止しない。旧部屋の条件を自動補完する例外も設けない。

## 4. 参加前に見せる情報と権限

実装したRPC：`wp_preview_room(p_room_code text)`。
Next.jsからは `GET /api/rooms/[roomCode]/preview` で呼ぶ。

対象は、匿名Authでログインしプロフィール登録済みのユーザー。部屋コードを知っている人に次の項目だけを返す。

- 部屋コード・グループ名
- 参加予定人数・現在の参加人数
- チャレンジ金額・起床日時
- 現在のユーザーが参加済みか
- 新規参加の可否と、その理由（満員・受付終了・時刻経過・旧部屋の条件未設定など）

参加者のユーザーID・ニックネーム・アイコン一覧は返さない。現在の `wp_get_room` の参加者限定チェックは残し、参加前の取得のために緩めない。条件確認だけでは `room_members` に行を作らず、人数枠も予約しない。

既存のRLS、直接テーブルアクセスの禁止、`SECURITY DEFINER` 関数の固定search_path、`auth.uid()` による本人確認を維持する。新しいRPCの実行権限は `authenticated` に限定し、`PUBLIC` と `anon` から取り消す。

## 5. RPC・APIの切り替え

作成・参加用のRPCは `wp_create_room_v25` / `wp_join_room_v25` とし、既存の関数名を使うフェーズ2との境界を明確にしている。入力・出力は改訂設計書に対応する。

| RPC | 引数 | 処理 |
| --- | --- | --- |
| `wp_create_room_v25` | `p_group_name text, p_max_members integer, p_wake_date date, p_wake_time time, p_challenge_amount integer` | 条件検証、wake_atの確定、部屋と作成者の同意済み参加を一括保存 |
| `wp_preview_room` | `p_room_code text` | 条件・人数・参加可否だけを取得 |
| `wp_join_room_v25` | `p_room_code text, p_accepted boolean, p_expected_wake_at timestamptz, p_expected_challenge_amount integer` | 保存条件との一致・同意・定員を確認し、参加とready判定を一括保存 |

ユーザーIDは引数に追加せず、`auth.uid()` を使う。起床日だけのDB列は不要で、`wake_at` に日付と時刻をまとめる。

新規参加では「条件を見た」というボタン操作に加え、表示した金額・起床日時を送信し、DBが保存している条件との一致を確認する。プレビュー後に日付をまたぐ場合や、移行中に条件が変わった場合は、不一致として再確認を求める。画面を実際に読んだかどうかをサーバーが保証する仕組みではない。

新しい参加RPCは、認証・プロフィール確認 → コード検証 → 部屋行のロック → 参加済みの確認 → 条件同意と一致の確認 → 新規参加可否の再確認 → 参加レコード追加、の順に処理する。
すでに参加している人への再送は、重複登録せず既存の部屋を返す。これは新しい条件への再同意を記録する操作には使わない。

同じ名前で引数だけを増やすと、既存の2引数 `wp_create_room` が残る可能性がある。旧RPCや旧APIを経由して条件なしで作成・参加できる状態を残さない。新APIに切り替えるタイミングで、旧作成・参加RPCの実行権限を取り消すか、明示的に呼び出しを拒否する。

ユーザーの決定により、作成後の条件変更は不可。条件更新RPC・版管理列・再承認APIは追加しない。金額や日時を変えて参加したい場合は別の部屋を新規作成し、参加者も改めてその部屋へ参加する。旧部屋の参加を自動的に移したり取り消したりしない。

### フェーズ3への接続

フェーズ2.5では、最後の参加登録時に全員の参加・同意を確認してreadyにするところまでを実装する。
フェーズ3では最後の参加登録と同じDBトランザクション内で、全員分の確認データを作成してactiveへ進める。手動開始APIや再承認は追加せず、部屋のポーリングやブラウザの起動状態に開始の成立を依存させない。
起床日時が未来であることを再検証し、開始処理の失敗時は最後の参加追加も取り消す。開始の再試行で確認データを重複作成しない。
フェーズ3では `wake_checks` の3番号の制約と `(room_id,user_id,check_number)` の一意性を追加し、checked_at・deadlineのtimestamptzへの統一を別途行う。既存timestampのタイムゾーンを確認してから移行し、値を推測して変換しない。

## 6. 既存データの扱い

フェーズ2で作った部屋には金額・時刻がNULLのものがあり、参加者の `approved` はfalseです。
100 WPや07:00などを勝手に埋めたり、既存メンバーを一括で承認済みにしたりしないでください。

移行方針は次のとおりです。

1. 適用前に既存部屋の件数、NULL・範囲外の値、承認状態、稼働中の部屋がないかを確認する。
2. 既存部屋を残せるよう、新しい `wake_at` はまずnullableで追加する。
3. 新規RPCではすべての条件を必須にする。移行中の列NULL許容は、新規部屋での条件省略を許す意味ではない。
4. 旧部屋は既存参加者が閲覧できるが、条件が整っていないものには新規参加や開始を認めない。新しい条件で参加したい場合は、新規部屋を作成して参加し直す案を採用する。
5. NULL・範囲外の値が残る間は、全体を一律にNOT NULL化しない。既存の不正値がCHECK追加を妨げる場合は、DB担当者の確認後に `NOT VALID` を使って新規データから保護し、既存データの整理後に検証する。
6. 旧部屋の削除や既存条件の変更が必要になった場合は、その対象を確認して別作業で行う。今回の移行で自動削除しない。

すでに条件を持つ既存部屋が見つかっても、参加者が今回のフローで同意した証拠にはならない。起床日時・同意が確定できない部屋は、自動的に新仕様の開始対象にしない。

## 7. 適用手順と戻し方

1. 改訂設計書とこの引き継ぎ書を共有する。日付選択・自動開始・条件変更不可はユーザー決定済み。
2. 検証環境で、既存フェーズ2スキーマに `supabase/phase2.5.sql` をファイル全体で適用する。すでに作成済みの4テーブルを作り直す必要はない。
3. 旧部屋を保持するテストと、新しい作成・プレビュー・参加テストを行う。
4. データバックアップ後、DB担当者とアプリ担当者が切り替え時刻を合わせる。切り替え中の作成・新規参加は一時的に止める。
5. 追加SQL、新API・画面、旧作成・参加RPCの無効化をそろえて反映する。
6. 実際の別ブラウザで作成・確認・参加・辞退・満員・再読み込みを確認して受付を再開する。

障害時は作成・新規参加を停止し、既存データを保持して原因を調べる。DBだけを戻して旧RPCの条件なし参加を再開すると、新仕様の同意確認を迂回できる。アプリとDBを対にして戻し、新仕様の部屋への旧フローからの参加は拒否する。データ列や同意記録をロールバックのために削除しない。

## 8. 受け入れ確認

- 100・2000 WPを保存でき、99・2001・小数・未入力を拒否する。
- 04:00・11:00を保存でき、03:59・11:01・秒付き・未入力を拒否する。
- 起床日時が全員に同じ日本時間で表示され、コード確認を翌日に行っても対象日がずれない。
- 過去の日付、存在しない日付、今日の過ぎた時刻を拒否する。同じ時刻でも未来の日付なら設定できる。
- 作成後の金額・時刻・日付の変更を拒否し、statusの更新は許可する。
- コード確認だけでは参加人数が増えない。「参加しない」も書き込みゼロ。
- 「この条件で参加する」で1件だけ追加され、作成者を含めて承認状態が正しい。
- 条件不一致、満員、受付終了、起床日時経過、条件のない旧部屋への新規参加を拒否する。
- 最後の1枠に2人が同時参加しても、定員を超えない。
- 非参加者に参加者一覧が返らず、未認証では条件取得RPCも実行できない。
- 古いコードや旧RPCを直接呼んでも、条件なしで新規作成・参加できない。
- SQLを繰り返し適用しても、データが消えず、旧RPCの権限が復活しない。

フェーズ3では、開始処理の重複実行で `wake_checks` が増えないことと、各参加者に3件ずつ作られることも確認する。

## 9. 今回の実装・検証結果

ローカルのPGliteで既存スキーマに移行SQLを適用し、旧データの保持・境界値・同意の必須化・条件変更禁止・readyへの遷移・旧入口の拒否・再適用を検証済みです。
ブラウザの画面テストは仮API応答を使っています。共有SupabaseへのSQL適用、実Authとの結合、複数DB接続での同時参加テストはDB担当者との実接続確認で行ってください。
移行後の実行コマンドと検証範囲の詳細は [実装と起動手順](phase2.5-implementation.md) を参照してください。
